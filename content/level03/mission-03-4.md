## STEP 1：今日覚えること（3分）

今日の新しい言葉は **3つだけ** です。

### ① Merge

| 観点 | 説明 |
|---|---|
| 正式な意味 | あるブランチの変更履歴を、別のブランチ（多くはmain）に統合すること |
| 初学者向け説明 | コピー（ブランチ）に書き込んだ内容を、正本（main）に清書して反映させる作業 |
| 現実世界での例え | 下書きコピーに書いた修正を、担当者が確認したうえで正式な原本に転記する |
| 実際の開発で何に使うか | 作業が完成したブランチをmainに取り込み、正式なバージョンとして確定させる |

### ② Squash Merge

| 観点 | 説明 |
|---|---|
| 正式な意味 | ブランチ内の複数のCommitを1つのCommitにまとめてから、mainへMergeする方式 |
| 初学者向け説明 | 途中経過のメモを何枚書いていても、mainには「完成した清書1枚」だけを残す方式 |
| 現実世界での例え | 何枚もの下書きメモを1枚の清書にまとめてから正本に綴じる |
| 実際の開発で何に使うか | あとから履歴を読む人（未来の自分やAI）が、途中の試行錯誤を追わずに「何が完成したか」だけを読めるようにする |

### ③ Delete branch

| 観点 | 説明 |
|---|---|
| 正式な意味 | Mergeが完了したブランチを、GitHub上（github.com）またはローカル上で削除する操作 |
| 初学者向け説明 | Mission 3-3で覚えた「ブランチの削除」と同じ操作を、github.com側のボタンからも行うこと |
| 現実世界での例え | Mission 3-3と同じ：役目を終えた下書きコピーを資源ごみとして処分する |
| 実際の開発で何に使うか | PRのマージ直後にgithub.com上に出てくる `Delete branch` ボタンを押すことで、その場で片付けまで完了できる |

> 💡 **今は覚えなくてよいこと**：Merge commit方式やRebase merge方式の違いの細部、コンフリクトが起きた場合のMerge戦略の選び方。本教材はSquash Mergeに統一するため、他の方式の使い分けはLEVEL 3では扱いません。

## STEP 3：何が起きたか確認（2分）

**今、リポジトリの設定の中で何が起きたのか。**

LEVEL共通の図（`content/level03/notional-machine-03.md`）を参照。通常のMergeは各Commitがそのままmainの歴史に積まれるが、Squash Mergeは複数Commitが1つにまとめられてからmainに積まれることを図で確認する。

**重要なポイントが2つあります。**

1. これは「今後作るPR全部」に効く設定である。docs/changelogのPRだけでなく、これから先ずっとSquash Mergeで統一される。
2. 設定を変えただけでは何も送信していない。GitHubの中の設定変更であり、郵送（Push）とは別の話。

---

> ### 🔍 なぜ？：なぜ Squash Merge に統一するのか
>
> **ひとことで**：あとから履歴を読む人（未来の自分やAI）が、途中の試行錯誤ではなく「完成した1つの変更」だけを追えるようにするためです。
>
> **もう少し詳しく**：作業中は「一旦保存」「typo修正」「やっぱり戻す」のような細かいCommitが自然に増えていきます。これをそのままmainの歴史に積むと、後から `History` タブを見返す人は、完成品にたどり着くまでの寄り道まで全部読まされることになります。Squash Mergeは、ブランチ内の全Commitを1つにまとめてからmainへ統合するので、mainの歴史は常に「意味のある1つの変更＝1つのCommit」の連続になります。
>
> **設計思想まで**：この教材がSquash Mergeに統一する最大の理由は、LEVEL 15でAI Agentが自分でPull Requestを作るようになったときに向けた準備です。Agentは人間よりも細かいCommitを大量に作りがちで、それを未整理のままmainに積み上げると、後から人間がレビューする際に「何が本当に変わったのか」を読み解くコストが跳ね上がります。今のうちからmainの歴史を「読みやすい単位」に保つ習慣をつけておくことで、将来Agentが作ったPRをレビューするときも同じ基準で読めるようになります。これは、履歴を「作業した証拠」としてではなく「後で読む人のための記録」として扱う、という設計判断です。情報を減らすことは一見もったいなく見えますが、読みやすさのために意図的に情報を捨てる、という判断がここにあります。
>
> **では、いつSquash Mergeを使ってはいけないか？** **複数人が同じブランチで並行作業し、各自のCommitを個別の記録として残したい場合**は、Squashで1つにまとめてしまうと「誰が何をしたか」が消えてしまいます。本教材は学習者1人で開発しているため、その場面は当面発生しません。将来チーム開発に入ったときは、この前提を見直す必要があります。

<details><summary>💡 ヒント1：方向（どこを見るか）</summary>

GitHub Desktopの右上のボタン（`Create Pull Request`）から始めます。あとはgithub.comのPR画面、Merge後に出てくるボタン、最後にGitHub Desktopの `Current Branch` の順に画面を移動します。
</details>

<details><summary>💡 ヒント2：手順（何をするか）</summary>

1. GitHub Desktopで `Create Pull Request` を押す
2. github.comでPRの説明を一言書き、緑のボタンでPRを作成する
3. PRページでMergeボタン（Squash表記）を押し、確認ボタンを押す
4. 出てくる `ブランチを削除`（Delete branch）を押す
5. GitHub Desktopに戻り `Current Branch` を `main` に切り替え、`Pull origin` を押す
</details>

<details><summary>💡 ヒント3：答え（完全な手順）</summary>

1. GitHub Desktopで `Create Pull Request` を押す（ブラウザでgithub.comが開く）
2. PRの説明欄に「CHANGELOG.mdを追加し、v0.1〜v0.4の履歴をまとめた」のように一言書き、`プルリクエストを作成する`（Create pull request）を押す
3. PRページで `スカッシュしてマージする`（Squash and merge）→ `マージを確定する`（Confirm squash merge）の順に押す
4. マージ後に出てくる `ブランチを削除`（Delete branch）を押す
5. GitHub Desktopに戻り、`Current Branch` を `main` に切り替える。上部に出る `Pull origin` ボタンを押し、GitHub上の最新状態（今マージした内容）をローカルのmainにも届ける
</details>

> ⚠ **つまずきポイント**：手順5の `Pull origin` を忘れると、次にmainで作業を始めたとき、自分のパソコンの中だけ古いmainのままになります。GitHubはDropboxのように自動で同期してはくれません。毎回「発送（Push）→受け取り（Pull）」の郵送のステップを自分で踏む必要がある、というDay1からの原則がここでも生きています。

**採点方針**：PRのMerge・ブランチ削除・Pull originの3点が完了していればクリア。**ヒントを開いてもクリア扱い（減点なし）。** できた部分を先に名指しして認めてから、残りを一緒に片付ける。

## STEP 6：理解チェック（2分）

暗記ではなく「なぜそうするのか」を確認します。

**Q1.** ブランチ内に5つの細かいCommitがあるとき、Squash Mergeを使うとmainの歴史には何個のCommitが残りますか？なぜですか？

<details><summary>解答</summary>
1個。5つのCommitを1つにまとめてからmainへ統合する方式だから。途中経過ではなく「完成した1つの変更」だけを歴史に残す。
</details>

**Q2.** リポジトリ設定でSquash Merge以外を無効にする理由は何ですか？

<details><summary>解答</summary>
mainの歴史を常に「読みやすい単位」に保つため。特に将来AI Agentが作るPRを人間がレビューするとき、細切れのCommitのまま積み上がると何が変わったのか読み解くコストが跳ね上がる。
</details>

**Q3.** Merge後に `Pull origin` を忘れると、次に何が起きますか？

<details><summary>解答</summary>
自分のパソコンの中のmainだけが古いままになり、次の作業がその古いmainの上で始まってしまう。GitHubは自動で同期しないため、毎回「発送→受け取り」を自分で行う必要がある。
</details>

**採点方針**：3問中2問の趣旨が言えていれば通過。**言葉が正確でなくても、現象の因果が説明できていれば正解扱いにする。** 誤答は復習対象として STEP7 の成長ログ項目3に書かせる。
