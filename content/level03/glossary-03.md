## 03-1-diff：差分（diff）

| 観点 | 説明 |
|---|---|
| 正式な意味 | 変更前と変更後のファイルを機械的に比較し、増えた行・減った行だけを抜き出して示したもの |
| 初学者向け説明 | 「どこが変わったか」だけを教えてくれる表示。ファイル全体を読み比べなくてよくなる |
| 現実世界での例え | 契約書の変更箇所に引いた赤線 |
| 実際の開発で何に使うか | AIが書いた変更を検証する中心スキル。LEVEL 12（AIの出力を検証する）とLEVEL 15（Dry-runのdiff確認）の土台になる |

## 03-1-add-del-lines：追加行・削除行（+ / -）

| 観点 | 説明 |
|---|---|
| 正式な意味 | 差分の各行に付く記号。`+`（緑）は変更後に増えた行、`-`（赤）は変更前から減った行 |
| 初学者向け説明 | 緑は「足したもの」、赤は「消したもの」。赤が出ても壊れたという意味ではない |
| 現実世界での例え | 契約書の赤線のうち、書き足した文言と、二重線で消した文言の区別 |
| 実際の開発で何に使うか | 1行だけ書き換えた場合も「削除1行＋追加1行」として表示される。AIの変更を見るときは、緑（増えたもの）だけでなく赤（消えたもの）が意図どおりかを必ず確認する |

## 03-1-rename：リネーム（ファイルの移動）

| 観点 | 説明 |
|---|---|
| 正式な意味 | ファイルの名前や置き場所を変える操作。Gitは内容の同一性から移動を推定するが、常に推定できるとは限らない |
| 初学者向け説明 | ファイルを別の場所へ移すこと。画面上は「元の場所から消えて、新しい場所に現れた」ように見えることがある |
| 現実世界での例え | 書類を別の引き出しへ移し替える（書類そのものは1枚のまま） |
| 実際の開発で何に使うか | GitHub Desktopでは `Renamed` の1行で表示されることも、「削除＋追加」の2行で表示されることもある。**どちらの見え方でも中身は失われていない**（CONTEXT.md §4 #2 の再発ポイント） |

## 03-2-history：History（履歴）

| 観点 | 説明 |
|---|---|
| 正式な意味 | リポジトリに積まれてきたCommitの一覧。時系列に並ぶ |
| 初学者向け説明 | これまで書いてきた作業日誌を、順番にめくって読み返せる機能 |
| 現実世界での例え | 作業日誌をページごとにめくって読み返すこと |
| 実際の開発で何に使うか | 「いつ・何が・なぜ変わったか」を後から追跡できる。Mission 3-6で「どこまで戻れば安全か」を判断する土台になる |

## 03-2-head：HEAD

| 観点 | 説明 |
|---|---|
| 正式な意味 | 今チェックアウトされているCommit（作業中の地点）を指すポインタ |
| 初学者向け説明 | 「今どのページを開いているか」を示す栞（しおり） |
| 現実世界での例え | 「現在地」のピン |
| 実際の開発で何に使うか | 通常は最新Commitを指している。BOSS 1で「どのCommitが原因か」を特定する際、HEADの位置と混同しないことが重要になる |

## 03-2-commit-hash：Commitハッシュ

| 観点 | 説明 |
|---|---|
| 正式な意味 | 各Commitに割り振られる一意のID（英数字の文字列） |
| 初学者向け説明 | 各Commitに付けられる「番号」。長いが先頭の数文字だけでも実用上は区別できる |
| 現実世界での例え | 宅配便の伝票番号（長い番号だが、先頭の数文字だけ伝えれば大抵特定できる） |
| 実際の開発で何に使うか | AIに「このCommitを見て」と伝えるとき、先頭7文字だけで十分。BOSS 1やLEVEL 9でAIとCommitの話をするときに使う |

## 03-3-branch-naming：Branch命名規則（feature/ fix/ docs/）

| 観点 | 説明 |
|---|---|
| 正式な意味 | ブランチ名の先頭に、作業の種類を表す接頭辞をつける命名の約束事 |
| 初学者向け説明 | 名前を見ただけで「新機能」「不具合修正」「文書」のどれかが分かるようにする |
| 現実世界での例え | 案件フォルダの背表紙に貼るラベルを、新機能用・不具合用・文書用の3色に貼り分けておく |
| 実際の開発で何に使うか | `feature/` は新機能、`fix/` は不具合修正、`docs/` は文書。この3つだけ覚えれば足りる |

## 03-3-current-branch：Current Branch

| 観点 | 説明 |
|---|---|
| 正式な意味 | 今、作業対象になっているブランチを示すGitHub Desktop左上の表示 |
| 初学者向け説明 | 「今どのコピーの上で作業しているか」を教えてくれる表示板 |
| 現実世界での例え | 今、自分の机の上にどの案件のコピーを広げているかを示す札 |
| 実際の開発で何に使うか | ファイルを編集する前に必ずここを確認する。mainのつもりで作業していたら実は別ブランチだった、という事故を防ぐ |

## 03-3-delete-branch：ブランチの削除

| 観点 | 説明 |
|---|---|
| 正式な意味 | Mergeが完了し役目を終えたブランチを、リポジトリの一覧から消す操作 |
| 初学者向け説明 | もう使わないコピーを片付けること。中身は正本にすでに転記済みなので消えるのは「コピーという名札」だけ |
| 現実世界での例え | 役目を終えた下書きコピーを、シュレッダーではなく普通の資源ごみとして処分する（正本には既に清書済み） |
| 実際の開発で何に使うか | Mergeが終わったブランチを溜め込まず片付ける。github.com側の `Delete branch` ボタンも同じ操作（Mission 3-4） |

## 03-4-merge：Merge

| 観点 | 説明 |
|---|---|
| 正式な意味 | あるブランチの変更履歴を、別のブランチ（多くはmain）に統合すること |
| 初学者向け説明 | コピー（ブランチ）に書き込んだ内容を、正本（main）に清書して反映させる作業 |
| 現実世界での例え | 下書きコピーに書いた修正を、担当者が確認したうえで正式な原本に転記する |
| 実際の開発で何に使うか | 作業が完成したブランチをmainに取り込み、正式なバージョンとして確定させる |

## 03-4-squash-merge：Squash Merge

| 観点 | 説明 |
|---|---|
| 正式な意味 | ブランチ内の複数のCommitを1つのCommitにまとめてから、mainへMergeする方式 |
| 初学者向け説明 | 途中経過のメモを何枚書いていても、mainには「完成した清書1枚」だけを残す方式 |
| 現実世界での例え | 何枚もの下書きメモを1枚の清書にまとめてから正本に綴じる |
| 実際の開発で何に使うか | あとから履歴を読む人（未来の自分やAI）が、途中の試行錯誤を追わずに「何が完成したか」だけを読めるようにする |

## 03-4-delete-branch-remote：Delete branch（github.com側）

| 観点 | 説明 |
|---|---|
| 正式な意味 | Mergeが完了したブランチを、GitHub上（github.com）またはローカル上で削除する操作 |
| 初学者向け説明 | Mission 3-3で覚えた「ブランチの削除」と同じ操作を、github.com側のボタンからも行うこと |
| 現実世界での例え | Mission 3-3と同じ：役目を終えた下書きコピーを資源ごみとして処分する |
| 実際の開発で何に使うか | PRのマージ直後にgithub.com上に出てくる `ブランチを削除`（Delete branch）ボタンを押すことで、その場で片付けまで完了できる |

## 03-5-conflict：Conflict（コンフリクト／衝突）

| 観点 | 説明 |
|---|---|
| 正式な意味 | 同じファイルの同じ箇所が `main` とブランチで異なる内容に変更されており、Gitがどちらを採用すべきか自動判断できない状態 |
| 初学者向け説明 | 正本側でも「ここをA案に」、コピー側でも「ここをB案に」となっていて、清書係（Git）が「どっちが正式版ですか？」と聞いてきている状態 |
| 現実世界での例え | 同じ契約書の同じ条項を、2人が別々に書き換えて送ってきた |
| 実際の開発で何に使うか | 事故ではなく、Gitが「判断できないので人間に返します」と正直に言っているだけ。**Gitが止めてくれるおかげで、片方の変更が黙って消える事故を防げている** |

## 03-5-conflict-marker：コンフリクトマーカー

| 観点 | 説明 |
|---|---|
| 正式な意味 | Gitが衝突箇所をファイルの中に直接書き込む記号。`<<<<<<< HEAD` から `=======` までが今いるブランチ側、`=======` から `>>>>>>> ブランチ名` までが取り込もうとしたブランチ側 |
| 初学者向け説明 | 「ここが揉めています」という印を、Gitがファイルの中に直接書き込んだもの |
| 現実世界での例え | 同じ契約書に、2人分の赤字修正が両方とも消されずに残っている状態（どこからどこまでが誰の修正かを線で区切ってある） |
| 実際の開発で何に使うか | この記号を読めれば「どこで・何と何がぶつかっているか」が分かる。**解決後は記号を1つ残らず消す**（消し忘れが最頻の失敗） |

## 03-5-resolve：Resolve（リゾルブ／解決）

| 観点 | 説明 |
|---|---|
| 正式な意味 | マーカーで示された両方の内容を人間が確認し、最終的に残す内容を決めて、マーカーの記号をすべて削除する作業 |
| 初学者向け説明 | 揉めている2つの案を見比べて「今回はこっちを採用する」（または両方を組み合わせた新しい文にする）と決めて、印を消すこと |
| 現実世界での例え | 契約書の2つの赤字修正を見比べて、どちらを正式な文言として清書し直すか決め、赤字の印を消して正本を完成させる |
| 実際の開発で何に使うか | Resolveが終わって初めて、Gitはそのファイルを「解決済み」とみなし、`Commit merge` でMergeを完了できるようになる |

## 03-6-revert：Revert（リバート）

| 観点 | 説明 |
|---|---|
| 正式な意味 | 過去の特定のCommitの変更内容を打ち消す、新しいCommitを作成する操作。元のCommit自体は削除されず履歴に残る |
| 初学者向け説明 | 「さっきの変更、やっぱりナシで」という取り消しを、新しい1行として日誌に書き足すこと |
| 現実世界での例え | 訂正印を押して差し戻す（元の記録は残る） |
| 実際の開発で何に使うか | AIが加えた変更が意図と違ったときに安全に戻す。取り消し自体も取り消せる。「壊しても戻せる」確信が、LEVEL 15でAI Agentに書き込み権限を渡す前提になる |

## 03-6-restore：Restore（変更の破棄）

| 観点 | 説明 |
|---|---|
| 正式な意味 | まだCommitしていない手元だけの変更を、直前のCommit時点の内容に戻すこと。GitHub Desktopでは対象ファイルを右クリックして `Discard changes`（変更を破棄する）を選ぶ |
| 初学者向け説明 | まだ日誌に書いていない書き損じのメモを、そのまま丸めて捨てること |
| 現実世界での例え | 清書する前の書き損じのメモを、日誌に書く前に丸めて捨てる（まだ記録していないので跡は残らない） |
| 実際の開発で何に使うか | Commit前の失敗はこれで戻す。**すでに日誌に書いてしまった（Commit済みの）内容を戻すには `revert`（訂正印）を使う**——これが2つの操作の境界線 |

## 03-6-reset：Reset（リセット／本教材では使わない）

| 観点 | 説明 |
|---|---|
| 正式な意味 | HEADとブランチの位置を強制的に過去のCommitへ戻す操作。指定地点より新しいCommitの記録そのものが消える（`--hard` では作業内容も消える） |
| 初学者向け説明 | 日誌のページそのものを破り捨てて、なかったことにすること |
| 現実世界での例え | 記録ごと破り捨てる（**本教材では使わない**） |
| 実際の開発で何に使うか | **本教材では使い方を教えません。** AIが `git reset --hard` を提案してきても実行しないでください（①実行しない ②「`revert` でできませんか」と聞き返す ③それでも必要なら人間に相談）。理由は Mission 3-6 の「🔍 なぜ？」で扱う |

## 03-7-terminal：Terminal（ターミナル）

| 観点 | 説明 |
|---|---|
| 正式な意味 | 文字でコマンドを入力してコンピュータに指示を出す画面。VS Codeには `Terminal` → `New Terminal` で開ける組み込み版がある |
| 初学者向け説明 | ボタンではなく文字で操作する画面。今日打つのは「見るだけ」のコマンドだけなので、打ち間違えても何も壊れない |
| 現実世界での例え | 窓口の担当者に口頭で用件を伝える代わりに、所定の書式で申請票を1枚出す（新規比喩ではなく、既存の「オフィス」世界観の範囲内） |
| 実際の開発で何に使うか | AIが提示するコマンドを**読める**ようになるための場所。LEVEL 9「AIが提示するコマンドを読む」の土台。本教材では操作の主役は今後もGUI（GitHub Desktop） |

## 03-7-git-status：git status

| 観点 | 説明 |
|---|---|
| 正式な意味 | 現在の作業ツリーの状態（Commitされていない変更があるか）を表示する読み取り専用コマンド |
| 初学者向け説明 | 「今、まだ記録していない変更があるか」を文字で確認するコマンド |
| 現実世界での例え | GitHub Desktopの `Changes` タブと同じ情報（＝まだ箱詰めしていない荷物の一覧）を、文字で見るだけ |
| 実際の開発で何に使うか | GUIの `Changes` タブと同じ情報が返る。実行しても中身は一切変わらない |

## 03-7-git-log-oneline：git log --oneline

| 観点 | 説明 |
|---|---|
| 正式な意味 | Commit履歴を1行ずつ要約表示する読み取り専用コマンド。各行の先頭に短縮Commitハッシュが付く |
| 初学者向け説明 | これまでのCommitを1行ずつ並べて見るコマンド |
| 現実世界での例え | 作業日誌をページごとにめくって読み返すこと（`03-2-history` と同じ比喩。新しい比喩は当てない） |
| 実際の開発で何に使うか | GUIの `History` タブと同じ情報が返る。先頭の英数字はエラーではなくCommitハッシュ（`03-2-commit-hash`）で、revertで対象を特定するのに使われている |
