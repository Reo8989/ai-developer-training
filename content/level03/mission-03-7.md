**質問と模範解答（学習者には見せていない前提）**

1. Q. Mission 3-6でrevertを実行すると、Gitの履歴には何が起きましたか？
   A. 新しいCommitが1つ積まれた。壊れた変更を打ち消す内容のCommitが追加されるだけで、元のCommit（壊した記録）も消えていない。「訂正印を押して差し戻す」の比喩どおり、履歴は残ったまま。

## STEP 2：実際にやる（5分）

> 📢 **予告**：今日打つのは、打ち間違えても何も壊れないコマンドだけです。「見るだけ」のコマンドなので安心してください。

1. VS Codeのメニューバーから `Terminal` → `New Terminal` をクリックしてください。画面下部に黒い入力欄（ターミナル）が開きます。
   - なぜ？：GUIの裏側で実際に何が起きているかを、同じ操作をCLIで再現しながら確認するためです。
2. ターミナルの入力欄をクリックしてから、`git status` と入力してEnterキーを押してください。実行する前に一度予想してみましょう：何が表示されると思いますか？
   実行すると、今Commitされていない変更がなければ `nothing to commit, working tree clean` のような表示が出ます。これはGitHub Desktopの `Changes` タブが空の状態と同じ意味です。

> ⚠ **つまずきポイント**：ターミナルの入力欄をクリックし忘れると、キーボードで打った文字がVS Codeの別の場所（エディタ側）に入ってしまうことがあります。文字を打つ前に、必ずターミナルの黒い入力欄をクリックしてください。

3. 続けて `git log --oneline` と入力してEnter。予想：これまでのCommitの記録は、どんな見た目で表示されると思いますか？
   実行すると、直近のCommitから順に1行ずつ、先頭に短い英数字、そのあとにCommitメッセージが並びます。これはGitHub Desktopの `History` タブと同じ情報です。

> ⚠ **つまずきポイント**：各行の先頭に出る `a3f9c21` のような英数字を見て、エラーが出たと勘違いするかもしれません。これはエラーではなく、そのCommitだけに割り振られた識別番号です。詳しくはこのあとSTEP5で扱います。

4. 続けて `git branch` と入力してEnter。予想：今のブランチ一覧はどう表示されると思いますか？
   実行すると、今リポジトリにあるブランチが一覧で表示され、今いるブランチの行にだけ `*` が付きます。GitHub Desktopの `Current Branch` の一覧と同じ情報です。
5. VS Codeで `README.md` を開き、末尾に `<!-- CLI practice -->` のような1行を追加してください。**`Cmd + S` で保存してください**（Commitはまだしません）。
6. ターミナルに戻り、`git diff` と入力してEnter。予想：今の変更はどう表示されると思いますか？
   実行すると、追加した行が `+` 付きで表示されます。Mission 3-1で読んだ差分と同じ見た目で、読み方を変える必要はありません。
7. 確認できたら、この練習用の変更はGitHub Desktopで元に戻します。`Changes` タブで `README.md` を右クリックし、`Discard changes`（変更を破棄）を選んでください。

## STEP 3：何が起きたか確認（3分）

**今、何が起きたのか。**

圧縮形式のため図は描きません。LEVEL 3共通の notional machine 図は `content/level03/notional-machine-03.md` を参照してください（Local/Remoteの関係は今日変わっていません。今日はローカルの状態を、ターミナルという「別の窓」からのぞき見しただけです）。

**重要なポイントが3つあります。**

1. `git status` / `git log --oneline` / `git branch` / `git diff` はどれも**「見るだけ」**のコマンドです。実行してもリポジトリの中身は一切変わりません。
2. GitHub Desktopの各タブ（Changes／History／Current Branchの一覧）は、実はこれらのコマンドが返す情報を、人間が読みやすい形に描き直しているだけです。裏側は同じGitです。
3. `git diff` の `+` `-` 表示は、Mission 3-1で読んだ差分と同じ見た目です。

**確認してみましょう：** GitHub Desktopを開いて `Changes` タブを見てください。さっきターミナルで見た `git status` の結果と、同じ状態になっているはずです。

---

> ### 🔍 なぜ？：GitHub DesktopというGUIがあるのに、なぜCLI（コマンド）も読めるようになる必要があるのか？
>
> **ひとことで**：これからAIが「このコマンドを実行してください」と提案してくる場面が増えていくからです。実行する前に、それが何をするコマンドかを自分で読んで判断できる必要があります。
>
> **もう少し詳しく**：今日扱った4つのコマンド（`git status` / `git log --oneline` / `git branch` / `git diff`）は、すべて「今の状態を見るだけ」で、実行しても何も変わりません。だから安全に触って慣れる練習ができます。一方で、この先AIがGitのコマンドを提案してくる場面（LEVEL 9以降）では、見るだけのコマンドとは限りません。実行してよいかどうかを判断するには、まず「読んで意味がわかる」ことが土台になります。
>
> **設計思想まで**：この教材は、GUI（GitHub Desktop）を操作の主役に据え続けています。理由は、GUIのほうが「今どの状態にいるか」を目で見て確認しながら作業できるため、初学者が事故を起こしにくいからです。だから、CLIをいきなり主役にして `git add` `git commit` `git push` まで手入力させる設計にはしていません。しかしLEVEL 9では「AIが提示するコマンドを読む」ことそのものが学習目標になり、さらにLEVEL 15ではAI Agentがリポジトリに対して直接コマンドを実行する権限を持つ設計になっています。そのときに学習者が「このコマンドが何をするか全く読めない」状態だと、AIの提案を無条件に信じてしまうか、逆に何も判断できず思考停止するかのどちらかになります。だから、操作の主役をGUIに残したまま、CLIを「読む」練習だけを今のうちに始めておきます。今日あえて `git add` や `git commit` を実行させなかったのも同じ理由です。読めることと、実行してよいと判断できることは別の技能であり、今日は前者だけを扱います。
>
> **では、いつCLIのコマンドを実行してはいけないか？** AIが提示したコマンドの意味を自分で読めていないとき、そして特に `git reset --hard` ・`rebase` ・`git push --force` のように履歴やファイルを壊しうるコマンドを提案されたときです。読めることと実行してよいことは別です。意味がわからないコマンドは、実行せずにまずAIか人間に聞き返してください。

## STEP 6：理解チェック（3分）

暗記ではなく「なぜそうするのか」を確認します。

**Q1.** `git status` を実行して `nothing to commit, working tree clean` と表示されました。これはどんな状態を意味しますか？なぜそう言えますか？

<details><summary>解答</summary>
今、ローカルにCommitされていない変更が1つもない状態です。GitHub Desktopの `Changes` タブが空になっているのと同じ状態で、コマンドが「見るだけ」で今の状態を教えてくれているからそう言えます。
</details>

**Q2.** `git log --oneline` の先頭にある英数字（例：`a3f9c21`）を、もし「読めないから消してもいい」と考えたとしたら、何が困りますか？

<details><summary>解答</summary>
その英数字は各Commitを一意に区別するIDです。Mission 3-6のrevertのように「このCommitを取り消す」と指定する操作は、このIDでCommitを特定しています。人間向けの要約（Commitメッセージ）とは別に、Git内部で正確に指定するために必要なものです。
</details>

**Q3.** 今日は `git add` や `git commit` をCLIでは実行しませんでした。なぜだと思いますか？

<details><summary>解答</summary>
変更を確定させる操作は、状態を目で見ながら安全に行えるGUI（GitHub Desktop）に任せ続けているためです。今日はCLIを「読んで理解する」練習に絞りました。この先LEVEL 9で「AIが提示するコマンドを読む」学習が始まり、LEVEL 15ではAI Agentが実際にコマンドを実行する権限を持つ設計になっています。読む力が先にあることで、その段階でも危険なコマンドを見分けられるようになります。
</details>

**採点方針**：3問中2問の趣旨が言えていれば通過。**言葉が正確でなくても、現象の因果が説明できていれば正解扱いにする。** 誤答は復習対象として STEP7 の成長ログ項目3に書かせる。
