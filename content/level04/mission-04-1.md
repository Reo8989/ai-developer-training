> ### 🔍 なぜ？：なぜ「完了条件」を先に書くのか
>
> **ひとことで**：完了条件が無いと、いつ終わったかを誰も判定できないからです。
>
> **もう少し詳しく**：目的や期待する結果は「思い」として書きやすい一方、完了条件は「確認できる事実」として書く必要があります。抽象的なままだと、依頼された側（未来の自分、あるいはAI）は「どこまでやればいいのか」を毎回自分で判断することになり、やりすぎたり、逆に不十分なまま終えたりします。
>
> **設計思想まで**：本カリキュラムには隠れた中核がある。それは「Issueを書く力＝AIに指示を出す力」という同型性である。今日渡した5要素（目的／現状／期待する結果／制約／完了条件）は、STEP5でAIに質問するときの8項目テンプレートの骨格と同じであり、さらにLEVEL15でAI Agentに仕事を渡すときの指示ともほぼ同じ構造になる。完了条件を先に決める発想は、AIに仕事を渡す場面でこそ効いてくる。人間の同僚なら、完了条件があいまいでも空気を読んで「このくらいでいいだろう」と止まってくれることがあるが、AIは空気を読まない。完了条件が書かれていなければ、判断基準が無いまま作業を続けるか、逆に早すぎるところで止まるかのどちらかになりやすい。BOSS-01で学んだ「復旧できるとわかっているから、大胆に任せられる」という考え方と対になる話がここにある。復旧できる安心があっても、そもそも何を頼んだのか・いつ終わりなのかが言葉になっていなければ、AIに仕事を渡すこと自体ができない。LEVEL 4はこの「渡し方」を教えるLEVELである。1人開発でIssueを書く意味も、この延長線上にある。今日Issueを書く相手は「未来の自分」でもある。数日後の自分は、今日の文脈を覚えていない。完了条件が具体的に書いてあれば、未来の自分もAIも、同じ基準で「終わったかどうか」を判定できる。LEVEL 15で、11レベル前の自分が書いたIssueをAI Agentが処理する設計になっている。そのとき、完了条件が曖昧なIssueをAgentに渡すと、Agentの成果物の質もそのまま曖昧になる。今日の完了条件の書き方が、11レベル先の成果物の質を先に決めている。
>
> **では、いつこれをやってはいけないか？** 思いついたことをとりあえずメモしておきたいだけの、1分で終わるような小さな気づきにまで、毎回5要素をきっちり書く必要はありません。後で自分やAIに実際に依頼する規模の作業に対してこそ、この型は効果を発揮します。

<details><summary>💡 ヒント3：答え（完全な手順）</summary>

完全な記入例（この通りの文章を求めているわけではありません）：

```
目的：進捗表の表示を、実際の到達点と一致させたい
現状：Mission 3-6を完了しているのに、進捗表の表示がMission 3-2のままになっている

制約：進捗表の見た目のデザインは変更しない。表示ロジックだけ直す
完了条件：Mission 3-6を完了した状態で進捗表を開き、Mission 3-6までのマスがすべて埋まっていることを目で確認できたら完了
```
</details>

## STEP 5：AIサポート（4分）

**まず、あなた自身の考えを書いてください。**（この欄が埋まるまで先に進みません）

> **★Q. Issue #1の完了条件は、今のままで、あなた自身（またはAI）が読んで「いつ終わったか」を判定できると思いますか？できないとしたら、何が足りないと思いますか？**
>
> [　　　　　　　　　　　　　　　　　　　　　　　　　　]

**仮説が書けないときに提示する選択肢（進行AI用）**
- (a) 完了条件はもう十分に書かれていて、何も変える必要はない
- (b) 目的や現状は書かれているが、「動くことを確認する」だけでは基準があいまいで、何をもって確認したことにするかが具体的でない
- (c) 完了条件ではなく、タイトルの書き方が不十分
- (d) 制約が書かれていないので、完了条件も意味をなさない

書けたら、AIに聞いてみましょう。

#### ❌ 悪い質問

> 「このIssue、レビューしてください。」

状況がゼロなので、AIは一般論の指摘しか返せません。どの要素が弱いのか、何を確認したいのかが伝わっていないからです。

#### ✅ 良い質問（8項目テンプレート適用）

```
【目的】書いたIssueの完了条件が、あとから判定できるレベルまで具体的になっているか確認したい
【現在の状態】Issue #2に完了条件として「進捗表を直す」と書いた
【環境】Mac / GitHub Desktop（英語UI）/ VS Code / github.com（日本語UI）
【再現手順】github.comの新しいIssue画面で、完了条件の欄に「進捗表を直す」とだけ書いて送信した
【エラー全文】エラーメッセージは出ていない。「直す」という言葉だけで、何をもって直ったとするかが書かれていないという状態
【自分の仮説】★「〜を確認できたら完了」という形になっていないので、あとで自分が読んでも判定できないのではないか
【制約】Issueの他の4要素（目的・現状・期待する結果・制約）は変えずに、完了条件の文章だけ直したい
【完了条件】完了条件の一文を読んだだけで、何を確認すればよいかが分かる状態になっていればよい
```

**このMissionで詰まったときに投げるプロンプト例**（進行AIが提示する）
- 「このIssueの完了条件『進捗表を直す』は、あとから確認できるレベルになっていますか？直すならどう書き換えればいいですか？」
- 「このIssueの5要素のうち、どれが一番弱いか指摘してください。」
- 「同じ内容のIssueを、AIへの指示文（8項目テンプレート）に書き換えるとどうなりますか？」

> 💡 **なぜ仮説を書かせるのか？**
> 仮説を立ててから答え合わせをすると、「合っていた／違っていた」という差分が記憶に残ります。今日のIssueの5要素は、この8項目テンプレートやLEVEL15のAgentへの指示と同型です。

## STEP 6：理解チェック（2分）

暗記ではなく「なぜそうするのか」を確認します。

**Q1.** 完了条件が書かれていないIssueを、未来の自分やAIに渡すと何が起きますか？なぜですか？

<details><summary>解答</summary>
いつ終わったかの基準が共有されていないため、やりすぎたり、逆に不十分なまま終えたりするズレが起きる。判断基準を都度自分で作ることになり、依頼した意味が薄れる。
</details>

**Q2.** 「MVP-0を作る」というIssueと、「MVP-Lを育てる」ためのタスクを同じ書き方で混ぜて書くと、どんな問題が起きますか？

<details><summary>解答</summary>
教材提供側が作る最小配布物（MVP-0）と、学習者が育てるアプリ（MVP-L）は担い手も範囲も別物である。混ぜて書くと「誰が」「どこまで」やる仕事なのかが曖昧になり、依頼として機能しなくなる。
</details>

**Q3.** Issueの5要素と、STEP5でAIに質問するときの8項目テンプレートが似ているのはなぜだと思いますか？

<details><summary>解答</summary>
どちらも「誰かに仕事を頼むときに必要な情報」という同じ構造をしているから。今日鍛えたこの力は、LEVEL15でAI Agentに仕事を渡すときにそのまま使う。
</details>

**採点方針**：3問中2問の趣旨が言えていれば通過。**言葉が正確でなくても、現象の因果が説明できていれば正解扱いにする。** 誤答は復習対象として STEP7 の成長ログ項目3に書かせる。
