## 04-1-issue-5-elements：Issueの5要素

| 観点 | 説明 |
|---|---|
| 正式な意味 | Issue本文を構成する5つの見出し：目的／現状／期待する結果／制約／完了条件 |
| 初学者向け説明 | 「何のために・今どうなっていて・どうなってほしくて・何を守って・どうなったら終わりか」の5つを分けて書くこと |
| 現実世界での例え | 業務依頼票（Issueの比喩）の記入欄が5つに分かれていること |
| 実際の開発で何に使うか | この5要素は、STEP 5 でAIに質問するときの8項目テンプレートの骨格であり、LEVEL 15 でAI Agentに渡す指示ともほぼ同じ構造。**「Issueを書く力＝AIに指示を出す力」がこのカリキュラムの隠れた中核** |

## 04-1-definition-of-done：完了条件（Definition of Done）

| 観点 | 説明 |
|---|---|
| 正式な意味 | その作業が終わったと判定するための、観測可能な条件 |
| 初学者向け説明 | 「何を確認できたら終わりにしてよいか」を、あとから読んだ人が判定できる形で書いたもの |
| 現実世界での例え | 業務依頼票の「検収条件」欄（何をもって受け取り完了とするかの取り決め） |
| 実際の開発で何に使うか | 5要素のうち**最も書きにくく、最も重要**。人間の同僚は曖昧でも空気を読んで止まってくれるが、AIは読まない。完了条件が無い依頼は、人間にもAIにも渡せない |

## 04-1-constraints：制約

| 観点 | 説明 |
|---|---|
| 正式な意味 | その作業で触ってよいもの・触ってはいけないものの線引き |
| 初学者向け説明 | 「ここは変えないでください」という但し書き |
| 現実世界での例え | 業務依頼票の「取扱注意」欄（この書類のこの部分は書き換えないこと） |
| 実際の開発で何に使うか | 制約が書かれていないと、依頼した範囲を超えた変更が返ってくる。Mission 3-6でAIにREADMEを丸ごと書き換えられた体験が、制約の必要性の実感になっている |

## 04-2-issue-template：Issue Template（イシューテンプレート）

| 観点 | 説明 |
|---|---|
| 正式な意味 | Issueを新規作成するときに、あらかじめ用意した定型フォーマット（見出しや記入欄）を自動で差し込む仕組み。`.github/ISSUE_TEMPLATE/` にMarkdownファイルとして置く |
| 初学者向け説明 | 毎回ゼロから書式を考えなくても、決まった項目が最初から入った状態でIssueを作れる仕組み |
| 現実世界での例え | 業務依頼票（Issueの比喩）を、白紙の用紙ではなく「あらかじめ項目が印刷された複写伝票」にしておくこと |
| 実際の開発で何に使うか | Mission 4-1で毎回頭で思い出していた5要素を、最初から入っている状態にできる。**GitHubが読みに行くのは既定ブランチ（main）に置かれたテンプレートだけ**なので、Branchに置いただけでは効かない |

## 04-2-labels：Labels（ラベル）

| 観点 | 説明 |
|---|---|
| 正式な意味 | Issueに貼る色付きのタグ。種類ごとに分類するための仕組み |
| 初学者向け説明 | Issueに貼る付箋の色。何の種類の依頼かひと目でわかるようにする |
| 現実世界での例え | 付箋の色分け |
| 実際の開発で何に使うか | `bug`（不具合）`enhancement`（改善）`docs`（文書）`learning`（学習用）の3〜5個に絞る。増やすほど「どれを貼るか毎回迷う」ようになり、分類として機能しなくなる |

## 04-2-dot-github-dir：`.github/` ディレクトリ

| 観点 | 説明 |
|---|---|
| 正式な意味 | GitHubがリポジトリの設定・自動化に使う、特別な名前のフォルダ。決まった場所（`ISSUE_TEMPLATE/` など）にファイルを置くと、GitHub側が自動で認識する |
| 初学者向け説明 | リポジトリの中にある「GitHub専用の設定コーナー」 |
| 現実世界での例え | 案件ごとのファイルキャビネット（Repositoryの比喩）の中にある、会社共通のルール・書式だけを収めておく専用の引き出し |
| 実際の開発で何に使うか | 今日はここにIssue Templateを置く。**ドット始まり・大文字小文字が1文字でも違うと認識されない**（CONTEXT.md §4 #4 の再発ポイント）。Finderでは作らず、必ずVS Codeで作る |

## 04-3-issue-reference：Issue参照（#番号）

| 観点 | 説明 |
|---|---|
| 正式な意味 | Issue・PR・Commitのメッセージ中に `#12` のように書くと、GitHub側が自動でIssue #12へのリンクに変換する記法 |
| 初学者向け説明 | 伝票番号（Issue番号）を、別の書類（PRやCommit）に書き添えると、自動でつながる仕組み |
| 現実世界での例え | 業務依頼票（Issueの比喩）の伝票番号を、対応する報告書に控えておくこと |
| 実際の開発で何に使うか | 「このBranch・このPRはどのIssueの作業か」が後から誰にでも辿れる。**Branch名に番号を入れただけではリンクされない**（リンクが張られるのはCommit messageやPR本文に `#番号` と書いたときだけ） |

## 04-3-closes-keyword：自動クローズ記法（Closes #番号）

| 観点 | 説明 |
|---|---|
| 正式な意味 | PR本文またはCommit messageに `Closes #12` と書くと、そのPRがmainにMergeされた瞬間にIssue #12が自動でCloseされる記法 |
| 初学者向け説明 | 「この依頼は片付きました」という印を、PRがMergeされた瞬間に自動で押してくれる仕組み |
| 現実世界での例え | 業務依頼票を、完了と同時に自動で「完了済み」の引き出しに移してくれること |
| 実際の開発で何に使うか | Closeし忘れを防げる。ただし**完了条件を満たしていなくても機械的に閉じてしまう**。自信がないときは `Closes` を書かず `#番号` だけ書いて参照リンクを残し、確認後に手動でCloseする |

## 04-3-issue-numbered-branch：Issue番号付きBranch名

| 観点 | 説明 |
|---|---|
| 正式な意味 | Mission 3-3の命名規則（`feature/` `fix/` `docs/`）に、Issue番号を足した命名（例：`feature/12-add-progress-days`） |
| 初学者向け説明 | 下書きコピー（Branch）の表紙に、対応する伝票番号（Issue番号）を書いておくこと |
| 現実世界での例え | 下書きコピー（Branchの比喩）に、対応する業務依頼票の番号を書き添えておくこと |
| 実際の開発で何に使うか | Branch名を見ただけで「どのIssueの作業か」が分かる。**新しいルールではなく、Mission 3-3のルールに1要素足すだけ** |

## 04-4-pr-three-points：PR本文の3点（何を・なぜ・どう確認したか）

| 観点 | 説明 |
|---|---|
| 正式な意味 | Pull Requestの説明欄（Description）に書く、変更内容・判断理由・検証方法の3項目 |
| 初学者向け説明 | 「何をしたか」「なぜそうしたか」「ちゃんと動くか、どう確かめたか」の3行を書くだけ |
| 現実世界での例え | 回覧書（Pull Requestの比喩）の表紙に添える一言メモ（何のための書類で、なぜこの内容で、どう確認済みか） |
| 実際の開発で何に使うか | レビューする人（未来の自分・チームメイト・将来のAI）が、コードを1行も読まなくても変更の意味を把握できる。LEVEL 15でAI Agentが作るPRも同じ3点構成になるよう設計されている |

## 04-4-review：Review（レビュー）

| 観点 | 説明 |
|---|---|
| 正式な意味 | 提出された変更内容を、正本に反映する前に確認すること |
| 初学者向け説明 | 「この内容で本当に大丈夫か」を誰か（または自分）がチェックする工程 |
| 現実世界での例え | 上司の検収・品質確認 |
| 実際の開発で何に使うか | Mission 4-5で、自分自身のレビューとAIのレビューを比較する。Mission 4-4ではまず、自分でPRを読み返すセルフレビューだけを行う |

## 04-4-draft-pr：Draft PR（下書きプルリクエスト）

| 観点 | 説明 |
|---|---|
| 正式な意味 | 「まだレビュー準備ができていない」ことを示す状態で作成できるPull Request |
| 初学者向け説明 | 回覧書の下書き版。正式に提出する前に「途中経過ですが、方向性は合っていますか？」と机の上に置いておく仮の回覧 |
| 現実世界での例え | 回覧書（Pull Requestの比喩）の下書き版 |
| 実際の開発で何に使うか | 作業途中でも早めに共有したいときに使う。**Mission 4-4では使わない**（名前だけ知っておく） |
