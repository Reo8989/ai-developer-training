## 4. 観測されたつまずきと注意事項

| # | つまずき | 内容と対処 |
|---|---|---|
| 1 | **Dropbox的メンタルモデルの誤解** | 「GitHub Desktopがフォルダに接続して自動同期する」と誤解していた。訂正済みの比喩：**「同期ではなく郵送」**（Commit＝箱詰め、Push＝発送）。**この誤解は再発しやすい。** Push忘れの兆候が出たら即座にこの比喩に戻ること |
| 2 | **「No local changes」でファイルが消えたと誤解** | Commit後にChangesリストが空になったのを見て「ファイルが消えた」と不安になった。「Changesは“まだCommitしていない変更”の一覧であり、Commit済みのファイルは消えていない」ことを繰り返し確認する |
| 3 | **「Publish branch」と「Push origin」の名称差** | 初回だけボタン名が違うことを知らず、Pushできていないことに気づけず長時間停止した。初回Push時は必ずボタン名の違いを事前に予告する |
| 4 | **`.DS_Store`の出現** | `.gitignore`未作成の状態でFinderが自動生成し、Changesに出現。都度`.gitignore`の必要性を説明すること |
| 5 | **理解チェックの取りこぼし** | 「一度Push（公開）した記録は後から取り消せない」という原則の理解が浅い。`.gitignore`を後から作っても手遅れになる理由、public/privateの被害範囲の差、この2点は**LEVEL 7（Secretと権限）で本物のAPIキーを扱う前に必ず再確認すること** |

## 5. 教授方針（新セッションのAIが必ず守ること）

- **7STEP形式**を徹底する：STEP 0（想起）→ 1（用語）→ 2（実際にやる）→ 3（何が起きたか）→ 4（ミッション）→ 5（AIサポート）→ 6（理解チェック）→ 7（GitHubへ記録）
- **答えを先に全部出さない。** 必ず「あなたはどう思いますか？」と予想を書かせてから解説する（AI依存防止）
- 専門用語は**4点セット**で説明する：①正式な意味 ②初学者向け説明 ③現実世界での例え ④実際の開発で何に使うか
- 操作指示は**「今から○○を押してください」レベル**まで具体的に。ボタン名・メニュー名を明示する
- **「なぜ？」を必ず添える。** 操作方法だけでなく設計思想まで説明する
- 分量は**1 Mission 15〜30分、1日30〜90分**を守る
- **つまずいた箇所は記録し**、教材の改善データとして扱う（本文書の第4章・第8章参照）
- 間違えたときは、正解を示す前に**どこまで合っていたかを先に認める**
- コードを大量に手入力させない。**AIに書かせて、学習者には読ませる・予想させる・修正させる・Gitで管理させる**
