## 1. GitHub認証まわり

### 1-1. GitHub OAuth Apps と GitHub Apps：現在の違い・推奨

- 現行仕様の要点：
  - GitHub公式ドキュメントは明確に **GitHub Appsを推奨**している。理由は「fine-grained permissions（細粒度の権限設定）」「どのリポジトリにアクセスできるかを制御できる」「短命（デフォルト1時間）のトークンを使う」の3点。
  - OAuth Appsは`repo`スコープのような広い権限単位でしか許可できず、ユーザーが明示的に取り消すまでトークンが有効（長寿命）。
  - Webhookの扱いもGitHub Appsは組み込みで一元管理できるのに対し、OAuth Appsはリポジトリごとに個別設定が必要。
  - OAuth Appsの利用が推奨される数少ないケースは「エンタープライズレベルのリソースへのアクセスが必要な場合」（GitHub Appsがまだ対応しきれていない領域があるため）。
- 設計上の含意：
  - 学習アプリの「GitHub連携」機能（LEVEL 14／セクション23のセキュリティ原則「必要最小限の権限」）には、初心者にも権限が理解しやすく、かつ現在のベストプラクティスに沿う **GitHub App方式を採用する**のが妥当。OAuth Appの仕組みも教材としては「昔ながらの広い権限モデル」として比較対象に説明する価値がある。
- 出典：
  - https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps

### 1-2. Fine-grained Personal Access Token（PAT）の現状

- 現行仕様の要点：
  - Fine-grained PATは2025年3月18日に一般提供（GA）となり、既定で全Organizationで有効。組織所有者の承認フローが必要な場合がある。
  - GA化に伴い、他の製品と同様の破壊的変更ポリシーが適用されるようになり、本番運用にも推奨できる段階になった。
  - 監査面では`token_id`がすべてのAPI呼び出しに含まれ、監査ログでのフィルタリングが可能。
  - 現状の制限（未対応領域）：Enterpriseオブジェクト管理API、複数組織を跨いだ単一トークンでのアクセス、外部コラボレーターとしてのリポジトリ貢献、Internalリポジトリへのアクセス、Packages・Checks APIの呼び出しなどは、fine-grained PATでは未対応（classic PATが必要）。
  - GitHubは将来的にclassic PATの廃止を目指しているが、廃止時期は明言されていない（本調査時点で確定日は未確認）。
- 設計上の含意：
  - LEVEL 7（認証とセキュリティ）の教材で「PATを作るなら最初からfine-grained PATを使う」ことを標準として教えるべき。ただし、教材内でPackages/Checks APIなど一部機能を使う設計をする場合はclassic PATが必要になる可能性がある点に注意（現時点の学習アプリの用途ではrepo/issues/pulls中心なのでfine-grained PATで問題ない見込み）。
- 出典：
  - https://github.blog/changelog/2025-03-18-fine-grained-pats-are-now-generally-available/
  - https://github.blog/security/application-security/introducing-fine-grained-personal-access-tokens-for-github/

### 1-3. GitHub App の Installation Token / Permissions の仕組み

- 現行仕様の要点：
  - GitHub Appを組織・リポジトリに「インストール」すると、そのインストールに対してInstallation Access Tokenを発行できる。トークンはデフォルトで短命（約1時間）。
  - 権限（Permissions）はリソース単位（例：issues, pull requests, contents, metadata）かつ`read`/`write`などのアクセスレベル単位で細かく設定でき、インストール時にリポジトリ範囲（All repositories / Selected repositories）を選択できる。
  - REST APIの`apps`関連エンドポイント（`/app/installations`など）でインストール一覧・トークン発行を扱える。
- 設計上の含意：
  - AI Agentに「Read→提案→人間承認→Write」の段階的権限を与えるセクション23の設計原則と非常に相性が良い。GitHub Appの権限設定は「AI社員ごとに必要最小限の権限を与える」という教材の思想（LEVEL 14以降）を具体的に体験させる教材として最適。
- 出典：
  - https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation
  - https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app
  - https://docs.github.com/en/rest/apps/installations

## 2. GitHub REST API / GraphQL API

### 2-1. バージョニングと主要エンドポイント

- 現行仕様の要点：
  - REST APIは日付ベースのバージョニング方式。リクエストヘッダー`X-GitHub-Api-Version`で使用バージョンを指定する（例：`X-GitHub-Api-Version: 2026-03-10`）。
  - ヘッダーを省略した場合のデフォルトは`2022-11-28`。
  - 破壊的変更（パラメータ削除・必須化・操作削除など）は新バージョンでのみ導入され、旧バージョンは新バージョン公開後、最低24か月間サポートが継続される（`2022-11-28`は2028年3月10日までサポート予定と案内）。
  - サポート対象外のバージョンを指定すると`410 Gone`が返る。
  - 主要エンドポイント（学習アプリで使う想定）：`GET /repos/{owner}/{repo}`（リポジトリ情報）、`GET/POST /repos/{owner}/{repo}/issues`（Issue一覧・作成）、`GET /repos/{owner}/{repo}/pulls`（PR情報）、`GET /repos/{owner}/{repo}/commits`（コミット履歴）など、いずれも現行でも安定的に提供されている（個別のレスポンススキーマ細部は今回未検証）。
  - GraphQL API（`https://api.github.com/graphql`）は単一エンドポイントでクエリを組み立てる方式。今回のWeb調査ではGraphQL APIの2026年時点の詳細な変更点までは深掘りしておらず、REST APIとの使い分け（GraphQLは複数リソースを一括取得する場合に有利、REST APIは初心者にとって直感的でシンプル）という一般的な傾向は多くの二次情報で一致しているが、公式ドキュメントの一次情報での最新版の詳細比較は未確認。
- 設計上の含意：
  - 初心者向け教材では、まず理解しやすいREST APIから入り、`X-GitHub-Api-Version`ヘッダーを明示的に指定する習慣を教える（バージョン固定は「AIが古い仕様で書いたコードとの差異」を防ぐ実践的な意味を持つ）。GraphQLはLEVEL 6以降の発展的トピックとして扱うのが妥当。
- 出典：
  - https://docs.github.com/en/rest/about-the-rest-api/api-versions
  - https://github.blog/changelog/2026-03-12-rest-api-version-2026-03-10-is-now-available/
  - （GraphQL APIの詳細仕様：未確認。設計書作成時に`https://docs.github.com/en/graphql`を別途確認することを推奨）

### 2-2. Rate Limit（レート制限）

- 現行仕様の要点：
  - 認証なし：60リクエスト/時間（公開データのみ）。
  - 認証あり（PAT・OAuthトークンなど個人の代理でのリクエスト）：5,000リクエスト/時間。GitHub Enterprise Cloud組織に所属するアプリの場合は15,000リクエスト/時間に引き上げ。
  - GitHub Appのインストールトークン：基本5,000リクエスト/時間（Enterprise Cloud組織の場合15,000リクエスト/時間）。インストール先リポジトリ数が20を超えると、超過分1リポジトリごとに+50リクエスト/時間が加算され、上限は12,500リクエスト/時間。
  - これらとは別に「二次レート制限（secondary rate limit）」（同時リクエスト数など）も存在する。
- 設計上の含意：
  - 学習アプリ側のバックエンドで「AIが大量にGitHub APIを叩く」設計（Agent連携時）をする場合、レート制限超過のハンドリング（429エラー処理・リトライ）を教材化する価値がある（LEVEL 13以降のAI Agent×GitHub連携で必ず直面する現実的な課題）。
- 出典：
  - https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api
  - https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/rate-limits-for-github-apps

### 2-3. Webhookの現在の仕組み

- 現行仕様の要点：
  - Webhookは「GitHub上でイベントが発生した際に、指定URLへHTTPリクエスト（POST）を自動送信する」仕組み。APIポーリングと異なり、イベント発生時のみ通知されるため効率的。
  - 設定範囲はリポジトリ単位・組織単位・GitHub App単位（GitHub Appの場合は一元管理）などで作成可能。
  - ペイロード内容はイベント種別ごとに定義されている（詳細は`Webhook events and payloads`ページ）。
  - セキュリティ上、配信されたペイロードの署名検証（HMAC等）が推奨されている（詳細ページ`Validating webhook deliveries`は今回深掘りしていない）。
  - IPv6は現時点で非対応（将来対応予定と明記）。
- 設計上の含意：
  - LEVEL 9（GitHub Actions・CI/CD）やLEVEL 13（GitHub×AI Agent）で「Issueが作られたらAI Agentが起動する」ようなHuman-in-the-loop設計をする場合、Webhook＋署名検証は必須の学習項目。ただし初心者に自前Webhookサーバーを立てさせるのは複雑度が高いため、まずはGitHub Actionsの`on: issues`トリガー（webhookの仕組みをGitHubが肩代わりしてくれる）で体験させ、自前Webhook実装は発展課題にするのが現実的。
- 出典：
  - https://docs.github.com/en/webhooks/about-webhooks
  - https://docs.github.com/en/webhooks/webhook-events-and-payloads
  - Webhookペイロードの署名検証の詳細手順：今回未検証（未確認）

## 3. GitHub Actions：基本構造と無料枠

- 現行仕様の要点：
  - Workflowは`.github/workflows/*.yml`にYAML形式で定義。`on:`でトリガー（push, pull_request, issues, schedule, workflow_dispatch等）、`jobs:`でジョブ、`steps:`で個別ステップを記述する基本構造は現行も変わらない。
  - Secretsはリポジトリ／組織／環境（Environment）単位で設定でき、`${{ secrets.NAME }}`で参照。
  - OIDC（OpenID Connect）による認証：クラウドプロバイダー（AWS/Azure/GCP等）に対し、長期の静的シークレットを保存せず、ワークフロー実行時に短命トークンを発行して認証する仕組みが公式に提供されている（`permissions: id-token: write`を設定して利用）。
  - 無料枠（2026年時点）：
    - **パブリックリポジトリ**：GitHub-hostedランナー（Linux/Windows/macOS）はすべて無料・無制限。
    - **プライベートリポジトリ（Freeプラン）**：Linux 2,000分/月、Windowsは実効1,000分相当（2倍レート消費）、macOSは実効200分相当（10倍レート消費）、ストレージ500MB。
    - 超過後の従量課金（2026年1月改定後の料金の一例）：Linux 2コア $0.006/分、Windows 2コア $0.010/分、macOS 3〜4コア $0.062/分。
    - その他の制限：単一ジョブ最大実行時間6時間、ワークフロー全体の最大期間35日、Freeプランの同時ジョブ数20。Freeアカウントはデフォルトの支出上限が$0のため、超過時は自動課金されずジョブが停止する。
- 設計上の含意：
  - 学習アプリの検証用リポジトリはパブリックリポジトリにしておけば、GitHub Actionsの分数を気にせず何度もCI/CDを試せる（初心者のもっとも大きな不安要素である「課金されるかも」という懸念を最初から解消できる設計判断として明記する価値がある）。OIDCはAI会社構築フェーズ（Vercelやクラウドへのデプロイを本格運用する段階）で「長期シークレットを持たない」設計思想を教える題材として有効。
- 出典：
  - https://cicdcalculator.com/github-actions-free-tier（二次情報。数値は複数の二次情報で一致しているが、GitHub公式の`https://docs.github.com/en/actions/administering-github-actions/usage-limits-billing-and-administration`および`https://github.com/pricing`での一次情報の再確認を推奨）
  - https://docs.github.com/actions/deployment/security-hardening-your-deployments/configuring-openid-connect-in-cloud-providers
  - GitHub Actionsのworkflow YAML基本構文の一次ソースページ：今回個別に取得していないため「未確認」。設計書作成時に`https://docs.github.com/en/actions/writing-workflows`を確認することを推奨。

## 4. AI API（2026年8月時点）

### 4-1. Anthropic API

- 現行仕様の要点：
  - 現行モデルファミリー（2026年8月時点、公式ドキュメント記載）：
    - **Claude Fable 5**（`claude-fable-5`）：最上位・最先端モデル。長時間実行のエージェント向け。1Mトークンのコンテキストウィンドウ、最大出力128kトークン、常時アダプティブシンキング。
    - **Claude Opus 5**（`claude-opus-5`）：複雑なエージェント型コーディング・エンタープライズ業務向け。
    - **Claude Sonnet 5**（`claude-sonnet-5`）：速度と知能のバランス型（汎用推奨モデル）。
    - **Claude Haiku 4.5**（`claude-haiku-4-5-20251001`）：最速・軽量モデル。
  - Messages API（`client.messages.create()`）が引き続き中心的なAPI。
  - Tool Use：ユーザー定義の「Client Tools」（アプリ側で実行し結果を返す）と、Anthropicのインフラ上で実行される「Server Tools」（web_search, web_fetch, code_executionなど）の2種類がある。`tool_choice`（auto/none/any/tool指定）や並列ツール呼び出し制御（`disable_parallel_tool_use`）に対応。
  - Structured Output：カスタムツール定義に`strict: true`を付与する「Strict Tool Use」機能により、Claudeのツール呼び出しがスキーマに完全準拠することを保証できる。
  - Agent SDK：Claude Codeと同じエージェントループ・ツール・コンテキスト管理をライブラリとして提供（Python/TypeScript対応）。組み込み機能はRead/Write/Edit/コマンド実行/Web検索などの組み込みツール、Hooks、Subagents、MCP接続、Permissions（自動実行 vs 承認要）、Sessions、Skills/Commands/Memory、Pluginsなど。CLI（Claude Code）とは別に、直接API呼び出し用の「Client SDK」、Anthropicがホスティングする「Managed Agents」という選択肢もある。
  - 料金体系：モデルごとにInput/Output トークン単価が異なる従量課金制（例としてFable 5はInput $10/output $50 per Mトークンという情報あり）。Batch APIやPrompt Cachingによる割引が用意されている一般的傾向は他社と共通だが、Anthropic公式の最新料金ページ（anthropic.com/pricing）は今回403エラーで直接取得できず、価格の詳細（Batch割引率、Prompt Caching割引率の正確な数値）は**未確認**。
- 設計上の含意：
  - LEVEL 10（AI API入門）でモデル名を教材に固定表記すると数か月で陳腐化するため、「モデル名は変わるものとして、アプリ内では環境変数でモデルIDを切り替えられる設計にする」ことを明示的に教えるべき。Structured Output（strict tool use）は「AI Tutor」機能や「AI社員のOutput」を安定したJSON形式で受け取る設計の基盤として重要。
  - Agent SDKの存在は、LEVEL 12以降（AI Agent入門〜AI会社構築）の設計の土台として非常に重要。ただし「Anthropicは第三者開発者がclaude.aiログインやレート制限をエージェント製品に転用することを許可していない」旨の注記があり、教材アプリでAgent SDKを使う場合は独自のAPIキー認証が前提になる点に注意。
- 出典：
  - https://platform.claude.com/docs/en/about-claude/models/overview
  - https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview
  - https://code.claude.com/docs/en/agent-sdk/overview

### 4-2. OpenAI API

- 現行仕様の要点：
  - 現行モデルファミリーは**GPT-5.6**（2026年7月公表）で、`gpt-5.6-sol`（フラッグシップ、高性能）／`gpt-5.6-terra`（中間）／`gpt-5.6-luna`（軽量・低価格）の3段階構成。
  - 主要APIは**Responses API**で、「テキスト、構造化出力、ツール、マルチモーダルワークフローへの直接モデルリクエスト」を扱う中核APIとして位置づけられている。
  - Tool Calling：プログラマティックなツール呼び出し制御、再利用可能なツールセットを構築する「Skill」機能、MCP統合による外部データソース接続などが「Tools」カテゴリとして整理されている。
  - 料金体系（1Mトークンあたり、例）：
    - gpt-5.6-sol：Input $2.50 / Cached input $0.25 / Output $15.00（Long context時はInput $5.00 / Output $22.50）
    - gpt-5.6-terra：Input $1.00 / Cached input $0.10 / Output $6.00
    - gpt-5.6-luna：Input $0.10 / Cached input $0.01 / Output $0.60
    - Batch処理は標準レートから50%割引。Fast mode（旧Priority processing）は標準の4倍。キャッシュ済み入力は通常の90%割引。2026年3月5日以降のモデルは地域処理により10%の追加料金が発生する場合がある。
- 設計上の含意：
  - Anthropicと同様、モデル名・料金は頻繁に変わるため、教材では「特定モデル名を覚えさせる」のではなく「モデルファミリーの選び方（速度・コスト・精度のトレードオフ）」という考え方を教えることが重要。「特定企業に依存しすぎない設計」という要件（LEVEL 10）に対応するため、教材アプリのAI呼び出し層を抽象化し、Anthropic/OpenAIどちらもプラガブルに扱える設計にすることの妥当性を裏付ける材料になる。
- 出典：
  - https://openai.com/index/gpt-5-6/
  - https://developers.openai.com/api/docs/pricing
  - https://developers.openai.com/api/docs

### 4-3. MCP（Model Context Protocol）

- 現行仕様の要点：
  - 2026年8月時点の最新仕様は**2026-07-28版**。最大の変更点は、プロトコルの中核が「双方向ステートフル」から「リクエスト/レスポンスのステートレス」構造へ転換したこと（`initialize`/`initialized`ハンドシェイクと`Mcp-Session-Id`ヘッダーが廃止され、各リクエストが自己完結するようになった）。これによりロードバランサー配下の任意のサーバーインスタンスでリクエストを処理できるようになった。
  - 主な新機能：Multi Round-Trip Requests（ステートレス下でのユーザー確認・入力）、ヘッダーベースルーティング、リスト応答のキャッシュ（`ttlMs`/`cacheScope`）、RFC 9207準拠のセキュリティ強化、実験段階から正式拡張になった`io.modelcontextprotocol/tasks`。
  - 普及状況：月間ダウンロード数が約5億件に達し、TypeScript・Python SDKはそれぞれ10億ダウンロードを突破。AWS、Google Cloud、Microsoft、Cloudflareなど主要クラウド事業者が対応を表明。Tier 1 SDK（TypeScript, Python, Go, C#）に加えRustのベータSDKもある。
  - **GitHub公式MCPサーバー**は存在する（`github/github-mcp-server`）。リポジトリ検索・ファイル参照・コミット分析、Issue/PRの作成・更新・管理、GitHub Actionsの監視・ビルド失敗分析、セキュリティ検出事項（Dependabotアラート等）の確認、Discussion/通知管理などをAIから自然言語で操作できる。リモートサーバー（VS Code 1.101以上やClaude Desktop等からOAuthまたはPATで認証）とローカル実行（Dockerイメージ`ghcr.io/github/github-mcp-server`、またはソースビルド）の両方に対応し、`--toolsets`で有効化する機能を絞り込める。
  - 参考として、Next.js 16には「Next.js DevTools MCP」という、AIエージェントがルーティング・キャッシュ・レンダリング挙動やログ、エラーを把握できるMCP統合が組み込まれている（フレームワーク側もMCPを前提にし始めている一例）。
- 設計上の含意：
  - MCPは2026年時点で「実験的技術」ではなく、主要クラウド・主要フレームワークが前提にし始めている業界標準に近い位置づけと言える。LEVEL 12〜13（AI Agent入門・GitHub×AI Agent）で「独自のツール呼び出しをゼロから設計する」学習に加え、「MCPという標準化されたツール接続方式がある」ことを紹介し、GitHub公式MCPサーバーを使えばGitHub操作ツールを自作しなくても良い、という選択肢を示すことは教育的価値が高い。ただしMCPサーバーの認証・権限設計はGitHub Appの権限モデルと組み合わせる必要があり、「初心者にすべてを自作させない」教材方針（セクション19）とも合致する。

## 5. Webフレームワーク・ホスティング（2026年時点）

### 5-1. Next.js

- 現行仕様の要点：
  - **Next.js 16**が現行メジャーバージョン（2025年10月21日リリース、その後16.3などのマイナーリリースあり）。App Routerが引き続き標準。
  - 主な特徴：Turbopackが安定版・デフォルトバンドラー化（開発時のFast Refreshが最大10倍、本番ビルドが2〜5倍高速）、Cache Components（`"use cache"`ディレクティブによる明示的キャッシュモデル、従来の暗黙的キャッシュから転換）、React Compiler対応（安定版、自動メモ化）、`middleware.ts`が`proxy.ts`にリネーム（非推奨化）、`create-next-app`が簡素化されApp Router・TypeScript・Tailwind CSS・ESLintがデフォルト構成に。
  - **Next.js DevTools MCP**が組み込まれ、AIエージェント（Claude CodeやCopilot等）がルーティング・キャッシュ・レンダリングの知識、ブラウザ/サーバーログの統合、スタックトレースへの自動アクセスを持てるようになった＝「AI駆動開発とのフレームワークレベルでの統合」が進んでいる。
  - Node.js 20.9+、TypeScript 5.1+が必須要件。
  - 初心者+AI開発との相性についての確定的な公式評価（Vercel自身の一次情報での明言）は今回未取得だが、DevTools MCPの存在自体が「AIエージェントとの協働を前提にフレームワークを設計している」という方向性を示す一次証拠になる。「初心者にとって複雑すぎる」という趣旨の批判的意見は多数の二次情報（ブログ等）で見られるが、これらは個人の見解であり公式見解ではない点に留意（**評価自体は未確認、批判の存在のみ確認**）。
- 設計上の含意：
  - Next.js 16は機能が非常に豊富（Cache Components, Turbopack, Server Actions等）で、初心者がいきなり全部を理解するのは負荷が高い。教材設計上は「Next.jsの機能のうち最初に触れるのはPage/Route/Server Component程度に絞り、Cache ComponentsやProxyなどの高度な機能はAI会社構築フェーズ以降に紹介する」という段階的導入が必要（これは設計書側で明確に指摘すべき過剰複雑化ポイント）。

### 5-3. Supabase

- 現行仕様の要点：

  - **Postgres**：SupabaseはマネージドPostgreSQLを提供。

## 6. その他：GitHub上でAIが働く公式機能／初心者のローカル環境構築回避策

### 6-1. GitHub Codespaces / github.dev

- 現行仕様の要点：
  - **GitHub Codespaces**：クラウドホスト型の開発環境（Dockerコンテナ上のLinux環境）。ブラウザ・VS Code・GitHub CLIから接続可能。個人アカウント（Free）の無料枠は**月120コア時間**（2コアマシンなら60時間相当）＋**ストレージ15GB**。超過後は従量課金（支払い方法登録が必要）。
  - **github.dev**：GitHub上のリポジトリ表示中に**ピリオド（`.`）キー**を押す、またはURLの`github.com`を`github.dev`に変えることで即座に開くブラウザベースの軽量エディタ。**無料・起動が一瞬**という利点があるが、コンピュート（実行・デバッグ・ターミナル）は一切なく、拡張機能もWeb対応版に限定される。ファイルの閲覧・編集・コミットのみ可能。
  - 両者の使い分け：軽い編集はgithub.dev、実行・デバッグを伴う本格的な開発作業はCodespacesという棲み分けが公式ドキュメント上でも示唆されている。
- 設計上の含意：
  - 本教材はMacでのローカル環境構築を前提としているが（セクション21：Macで開発可能）、初心者が最初につまずきやすい「ローカル環境構築（Node.jsのインストール、パスの通し方等）」を回避する選択肢として、LEVEL 0〜1の初期段階でgithub.dev（ファイル閲覧・簡単な編集体験）やCodespaces（実際にターミナルを使う体験）を導入教材として使うのは有効。ただしCodespacesは無料枠が月120コア時間と有限であるため、「メインの学習環境はローカル（VS Code）」「Codespacesは補助・体験用」という位置づけが妥当（無料枠を使い切って詰まる初心者を出さないため）。
- 出典：
  - https://github.com/features/codespaces
  - https://docs.github.com/en/codespaces/the-githubdev-web-based-editor

### 6-2. GitHub Copilot coding agent（GitHub上でAIが働く公式機能）

- 現行仕様の要点：
  - GitHub Copilot **coding agent**（cloud agent）は、Issue・チャットプロンプト・コメントなどでタスクを割り当てると、「リポジトリ調査→実装計画立案→GitHub Actions環境上でのコード変更→フィードバックへの反復対応→PR作成」という一連の流れを自律的に実行する公式機能。
  - 制限事項：最大実行時間59分、単一リポジトリでのみ動作、1セッションにつき1つのPRを作成。
  - 利用可能プラン：有償のCopilotプラン全般（Pro以上）で利用可能。Business/Enterpriseでは管理者による関連ポリシーの有効化が必要。
  - Copilotの料金プラン（2026年時点）：Free（$0、月2,000回のコード補完まで）／Pro（$10/月、無制限のコード補完・cloud agentとコードレビューへのアクセス・$15分の月次AIクレジット込み）／Pro+（$39/月、Opus等プレミアムモデルへのアクセス・$70分のAIクレジット込み）／Max（$100/月、新モデルへの優先アクセス・$200分のAIクレジット込み）／Business・Enterprise（組織向け、ポリシー管理・監査対応）。
- 設計上の含意：
  - これはまさに本教材が最終到達目標とする「AIがIssueを取得し、ブランチを作り、コードを変更し、PRを作る」というワークフロー（セクション3・LEVEL 13）を、GitHubが公式機能として既に提供していることを意味する。設計書では「教材の最終フェーズで自作するAI Agent連携は、GitHub Copilot coding agentという“完成品”と何が違うのか（自作する教育的価値：ツール呼び出し・権限設計・Human-in-the-loopの仕組みを“中身から”理解できる）」を明確に位置づけて説明する必要がある。またCopilot coding agentはFreeプランでは使えない（有償プラン必須）ため、無料の範囲で完結させたい教材の前提とは別軸の話として扱うべき。
- 出典：
  - https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent
  - https://github.com/features/copilot/plans
